# Infrastructure Reference

## Machines

| Machine | OS | LAN IPs | Access |
|---------|-----|---------|--------|
| Windows Host | Windows 10 + Docker Desktop (WSL2 backend) | `<ADSL_LAN_IP>`, `<STARLINK_LAN_IP>` | SSH: `ssh <user>@<STARLINK_LAN_IP>` (Windows native OpenSSH, port 22) |
| Mac (client) | macOS | varies | Developer machine |

## Network Layout

```
ADSL Network: 192.168.x.0/24
  Gateway/Router: 192.168.x.1
  Public IP: <your static public IP>
  Windows Host: <ADSL_LAN_IP>

Starlink Network: 192.168.x.0/24
  Gateway: 192.168.x.1
  Windows Host: <STARLINK_LAN_IP>
  Public IP: dynamic (CGNAT)
```

## Port Plan

| Port | Proto | Where | Purpose |
|------|-------|-------|---------|
| 22 | TCP | Windows host (native OpenSSH) | SSH into Windows for deploy |
| 1194 | TCP | Docker container (published to host) | OpenVPN server |
| 51820 | UDP | Docker container (published to host) | WireGuard server |

## Port Forwarding Chain (Docker)

### OpenVPN (TCP)

```
Internet:1194/TCP
  -> Router (<public_ip>:1194)
  -> Windows (<LAN_IP>:1194)
  -> Docker Desktop port publish
  -> openvpn container (TCP 1194)
```

### WireGuard (UDP)

```
Internet:51820/UDP
  -> Router (<public_ip>:51820)
  -> Windows (<LAN_IP>:51820)
  -> Docker Desktop port publish
  -> wireguard container (UDP 51820)
```

Docker Desktop handles both TCP and UDP port publishing natively. No
`netsh portproxy` or PowerShell UDP relay needed.

## Protocol Comparison

| | OpenVPN | WireGuard |
|--|---------|-----------|
| Protocol | TCP | UDP |
| Port | 1194 | 51820 |
| Docker port publish | Native TCP | Native UDP |
| Performance | Higher overhead (TCP-over-TCP possible) | Lower overhead, faster |
| Client apps | OpenVPN Connect, Tunnelblick | WireGuard app (all platforms) |
| Config format | .ovpn (cert-based PKI) | .conf (key-based, simpler) |

## Legacy (pre-Docker)

The previous setup ran VPN services directly on WSL2 with manual startup
scripts and Windows port forwarding. Key pain points that Docker solved:

- WSL2 internal IP changed on every reboot, requiring `netsh portproxy` refresh
- `netsh portproxy` doesn't support UDP, needed a custom PowerShell UDP relay
- `/dev/net/tun` had to be recreated after every WSL restart
- iptables rules were not persistent
- No auto-start; manual scripts after every reboot
- `/etc/resolv.conf` kept getting overwritten

The old scripts are preserved in `scripts/` for reference.
